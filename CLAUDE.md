# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

DebugX is a Windows-only GUI/CLI debugger front-end built on top of the Windows Debug Engine (DbgEng/`IDebugClient` COM APIs — `DbgEng.h`/`DbgModel.h`). It wraps `dbgeng.dll` to attach to live user-mode processes, launch executables under the debugger, open crash dumps, and attach to a local kernel debugger, then exposes process/thread/module enumeration and command execution to a WTL-based docking GUI.

## Build

This is a Visual Studio solution (`DebugX.sln`) with eight C++ projects of its own (plus the wtlhelper ones) (and, in its Tests folder, a test runner and four programs it debugs), built via MSBuild/Visual Studio.

WTL and the docking framework come from the `wtlhelper` git submodule (`git submodule update --init`): `wtlhelper/WTL` is the WTL 10.01 that every project compiles against, and `wtlhelper/WTLDock/WTLDock.vcxproj` (a static library, part of `DebugX.sln`) is the docking framework — see `wtlhelper/WTLDock/README.md` for its API — and `wtlhelper/WTLHelper/WTLHelper.vcxproj` (also part of the solution) is the helper library that provides dark mode, the toolbar builder, menu icons and the settings store. WTLHelper needs Detours and WIL from **vcpkg** (the static triplets); DebugX itself needs Scintilla and Lexilla (the Command view's output, and the Disassembly view's), and DebugX.Mcp (and the test runner) nlohmann-json: `vcpkg install detours wil scintilla lexilla nlohmann-json --triplet x64-windows-static`, and again for `x86-windows-static`. vcpkg's user-wide MSBuild integration must be on. `wtlhelper/HexControl` (behind the Memory view; also part of `DebugX.sln`, see below) needs nothing beyond `wtlhelper/WTL`; nor does `wtlhelper/MarkdownView` (the Assistant pane's transcript, `CMarkdownViewCtrl`, Direct2D/DirectWrite; also in `DebugX.sln`, read its `CLAUDE.md` before changing how the pane uses it). `DebugX.vcxproj` sets `VcpkgUseStatic` so it links the static-CRT builds (as do `DebugX.Mcp.vcxproj` and `DebugEngineTests.vcxproj`). Remaining dependencies are restored via NuGet (`packages.config` per project): WIL (`Microsoft.Windows.ImplementationLibrary`) and `Microsoft.Debugging.DataModel.CppLib` / `Microsoft.Debugging.Platform.DbgEng` (DbgEng headers/import libs). Open `DebugX.sln` in Visual Studio and build/run normally, or use MSBuild (`MSBuild.exe DebugX.sln -p:Configuration=Debug -p:Platform=x64`); all four x86/x64 Debug/Release configurations build.

**Tests.** `Tests\DebugEngineTests` (x64 only, in the solution's Tests folder) tests `DebugEngine::DebuggerX` against small programs it debugs, `Tests\Targets\{loop,src,exc,scope,values,procs}` (projects `TestTarget.x`, built as `x64\<configuration>\Tests\x.exe` — always unoptimized debug builds with incremental linking, see `Target.props`; the tests depend on their line numbers and function names). Run `x64\Debug\DebugEngineTests.exe` after building the solution: with no arguments it runs every suite (`scope`, `bp`, `exc`, `src`, `next`, `dump`, `values`, `procs`, `remote`, `script`, `mcp`, `assistant`, `kernel` — `assistant` drives the Assistant's loop against a scripted `ITransport` that plays SSE streams (no network; with `DEBUGENGINETESTS_LIVE_API=1` and `ANTHROPIC_API_KEY` it also asks the real API one question — billed, SKIP otherwise), `mcp` drives DebugX.Mcp's server over HTTP from a worker thread while its tools run on the suite's message loop (`OnThread` awaits the worker; the test host's status is `g_Events.Status`, from `StatusChanged`), `remote` starts the Kits debugger's `dbgsrv.exe` over a named pipe (SKIP without it; System32's engine cannot connect to it, 0x8007053D, and says SKIP too), `script` runs JavaScript (SKIP on an engine without JsProvider); the last attaches to the local kernel and looks at the runner's own process; it needs an elevated runner, `bcdedit /debug on` and the kernel's symbols, and says SKIP without them) once with each `dbgeng.dll` — the Windows Kits debugger's (if installed; what `DebugX.exe` loads then), System32's (what it loads otherwise) and the NuGet package's (`DebugEngine\amd64`) — since they behave differently (it is delay-loaded and chosen with `DebugEngine::LoadEngine`; `--engine kits|system|package` picks one, suite names pick suites). The `kernel` suite runs fully only on the Kits engine (the others have no `symsrv.dll` for the kernel's symbols; System32's may also refuse the local kernel once a newer engine has loaded its kernel debugging driver); the exit code is the number of failed checks; with `DEBUGENGINETESTS_OUTPUT=1` in the environment it also prints the engine's output. Each suite is a coroutine on the runner's message loop with a `DebuggerX` of its own, as DebugX's windows use it. A change to the engine is not done until both engines pass; there are no UI tests.

## Projects

- **DebugEngine** (static lib) — the debugger API and its DbgEng implementation. `IDebugger.h` is the engine-neutral part: the types that go in and out (`ThreadInfo`, `BreakpointSettings`, `EventFilter`, the notification payloads, ...) and `DebugEngine::IDebugger`, the abstract interface the GUI uses — no `DbgEng.h`, COM or `DEBUG_*` in it (it does use the Windows base types, `ULONG`/`HRESULT`/`PCWSTR`/`HANDLE`, which another platform would supply), so that another engine (GDB, LLDB) can implement it. Its constants (`AnyId`, `FilterBreak`.../`FilterGoNotHandled`, `BreakOnRead/Write/Execute`, `AttachType`, `ExecutionStatus` — the `StatusChanged` payload) have DbgEng's numbers, since some are saved in settings; `Debugger.cpp` `static_assert`s that they still match. What an engine cannot do fails with `E_NOTIMPL` (the optional members — kernel, scripts, process server, dumps, handles, Analyze, thread freezing — default to that). Code locations are in the engine's syntax and made by the engine: `AddressLocation(address)`, `SourceLineLocation(file, line)`, used with `AddBreakpoint`, `RunTo` and `ResolveLocation`; with `Go`, `EndCurrentProcess(terminate)` and `StackPointerExpression` they replace the dbgeng commands the GUI used to send itself (`g`, `` `file:line` ``, `.kill`/`.detach`, `@$csp`) — the GUI should not put dbgeng syntax together, except in the DbgEng-only kernel panes (`dt nt!...`, `!object`, ...). `Dispatcher.h`: `IDispatcher::Post` runs a function on the UI thread; `CreateWindowDispatcher` (`WindowDispatcher.cpp`) is the Win32 one, a message-only window. `Debugger.h`/`.cpp` defines `DebugEngine::DebuggerX : IDebugger`, the DbgEng implementation (pImpl, `DebuggerX::Impl` owns the `IDebugClient7`/`IDebugControl7`/etc. COM pointers), plus what only it has: `RunAsync(IDebugClient*)` (the kernel analyzers), `LoadEngine`. `AsyncTask.h` is the coroutine `Task<T>` the calls return.
- **DebugX.Mcp** (static lib) — an MCP (Model Context Protocol) server through which AI clients (Claude Code, ...) investigate the target. `McpServer.h` is all a program sees: `McpServer(IMcpHost&)`, `Start(port, token)`/`Stop`; the host gives the `IDebugger`, the execution status (from `StatusChanged`: the library has no `SessionModel`), the target's name, and is told of each tool call (`ToolCalled`: DebugX logs it in the Output pane). Transport: MCP's Streamable HTTP, hand-rolled on Winsock (`McpServer.cpp`), on 127.0.0.1 only, path `/mcp`, POST only (JSON answers, no SSE; GET 405), every request with `Authorization: Bearer <token>` (DebugX may be elevated and `run_command` can do anything), Host and Origin checked against loopback (DNS rebinding); JSON-RPC `initialize`/`ping`/`tools/list`/`tools/call`, batches, notifications answered 202. A connection gets a thread of its own; tools run on the thread the server was started on (the UI thread, through a `CreateWindowDispatcher` of the server's): `ToolKind::Serialized` ones one at a time (a tool may switch the current thread or scope frame and switch it back across its `co_await`s — `EnterScope`/`LeaveScope`), `Immediate` ones (go, run_to, step: their task completes only when the target stops) at once, `WaitForStop` ones (break_into, wait_for_stop) by polling the status from the connection's thread; a tool not done within its timeout is answered as such and goes on (for a run: "still running", not an error). A run in flight counts as running (`ToolContext::RunsInFlight`) — the status is the old one until the engine's `StatusChanged` arrives, and `wait_for_stop` right after `go` would otherwise see "stopped". The tools are in `McpTools.cpp` (`Tools()`: name, schema, annotations, kind, timeout, coroutine), text results for the model, engine-neutral except `run_command` (WinDbg syntax) and `StopSummary`'s `.lastevent`; `get_source` only reads files the symbols name (a file and line must resolve through `ResolveLocation`), not any file. The server's `instructions` (`ServerInstructions`) tell the model how to use them. Two `IDebugger` members exist for it: `ExecuteCommandCaptured` (a command's output returned, not given to the Command view; a `g` waits as `ExecuteCommand`'s does) and `GetThreadStackTrace` (any thread's stack without switching: `Impl::InternalSwitch`, also what `EnumProcesses` uses). DebugX: Options > MCP Server (`CMcpServerDlg`: on/off, port — `AppSettings::McpPort`, default 47011 —, token — `McpToken`, made on first use —, the `claude mcp add` command to copy); `CMainFrame::ApplyMcpSettings` starts/stops it, at startup too; `RelaunchElevated` and `CancelKernelConnection` stop it first, so the new instance gets the port. **The Assistant** (same library, namespace `DebugX::Ai`) is the in-app conversation with Claude over the same tools: `ClaudeApi.h` is the Messages API without an SDK (C++ has none) — `SseParser`, `MessageBuilder` (stream events into the message, thinking signatures kept, a `tool_use` input parsed strictly at its block's end: the tools are declared with `eager_input_streaming`, so invalid input is answered `INVALID_JSON`, not run), `EchoContent` (what goes back after a server-side fallback block), `ITransport` (`CreateHttpTransport`: WinHTTP to api.anthropic.com, `anthropic-version: 2026-10-21`; `Cancel` closes the request handle from another thread). `Assistant.h` is the manual agent loop as a coroutine on the UI thread: each request runs on a worker thread whose events come back through the Assistant's window dispatcher (`Poster`, closed in the destructor); waits are a thread-pool timer (`DelayAwaiter`), not a blocked thread. Requests: `claude-opus-5-5` by default, adaptive thinking with `display: "summarized"` (shown dimmed), explicit `output_config.effort`, top-level `cache_control`, `fallbacks: "default"` (beta `server-side-fallback-2026-07-01`) on the models that take it, `max_tokens` 64000, streamed; `thinking.block_binding.prefix_mismatch_behavior: "drop_block"` (beta `thinking-binding-controls-2026-08-01`: a history mismatch drops thinking instead of a 400 -- a safety net); **compaction**: `context_management.edits` `compact_20260112` (beta `compact-2026-01-12`) at `AssistantOptions::CompactAtTokens` (150K; 0 off; at least 50K) with `CompactionInstructions` (which forbid tool calls: with tools declared the summarizing step could call one and leave no summary) -- the answer then starts with a `compaction` block (its summary in `content_block_start` or a `compaction_delta`; `MessageBuilder` takes either), which goes back with the rest like any block, and the API ignores what came before it; its tokens are only in `usage.iterations`, which the totals add. **The conversation is append-only** — thinking blocks are bound to the exact system prompt, tools and earlier messages (preserved thinking), so the system prompt and tool list are fixed and nothing sent is ever edited: the target's state goes in a `<debugger_state>` text block at the start of each user message, a refused answer is left out rather than trimmed, cancelled tool calls are answered as not run. Tools run through `RunInto`/polling with the MCP tools' timeouts (the same kinds: a `WaitForStop` tool waits for the stop here, on the UI thread); one that is not `ReadOnly` asks the `Approver` first. The pane is `CAssistantView` (View > Assistant, `PaneRegistry` id `assistant`): the conversation is a Markdown document built by `DebugX::Ai::Transcript` (`DebugX.Mcp/Transcript.h`, window-free and tested: answers `Linkify`d -- symbols and addresses, in prose or a lone code span, become `dbgx:` links, `LinkTarget` reads them back; `<` outside code escaped so a C++ type is not HTML; reasoning as a quote; a tool call a line while it runs, then a `<details>` with its result (300 lines / 30K characters) in a fence longer than any backtick run in it; errors as `[!WARNING]`) shown in a `CMarkdownViewCtrl` (`MDVF_HARDBREAKS`, `MDVS_NOLINKTIPS`; `MDVN_LINKCLICK`: `dbgx:` -> `GoToDisassembly`, http(s) -> the browser; `MDVN_CONTEXTMENU`: the pane's menu). `SetText` parses it all again and goes back to the top (and closes opened `<details>`, drops the selection): `Render` sets it at most every `RenderDelay` ms while pieces stream (at once for anything else) and puts the view back -- at the end if the end was showing, else at `GetTopOffset`. An input edit (Enter sends, Shift+Enter a line, Esc stops), the approval task dialog, `CAssistantSettingsDlg` (model, effort, `AppSettings::AssistantAllowControl`); the API key is in Windows Credential Manager (`ApiKey.h`, generic credential "DebugX/Anthropic API key"), else `ANTHROPIC_API_KEY`. The system prompt asks for GitHub Markdown with symbols in code spans. Its host is a `McpHost(false)` (no Output-pane log lines: the pane shows the calls); the target's name for both hosts is `SessionModel::TargetName`, which `CMainFrame::SetTargetName` sets.
- **DebugX.Kernel** (static lib) — kernel-mode analysis helpers used when attached to a live/local kernel target (`DebugX::Analysis` namespace): `KernelGlobals` (symbol/global lookup), `KernelProcessAnalyzer`/`KernelProcessEnumerator` (walks `_EPROCESS` via the debugger's symbol/data-space APIs), `KernelThreadAnalyzer`/`KernelProcessThreadEnumerator`, `KernelObjectAnalyzer` (the object manager's namespace from `ObpRootDirectoryObject`, an object's type through `ObTypeIndexTable`/`ObHeaderCookie` and its name through `ObpInfoMaskToOffset`; the driver objects of `\Driver` and `\FileSystem`; a thread's pending IRPs from `_ETHREAD.IrpList`). It is built as C++17. These are plain analysis classes, not an actual kernel driver, despite the project name.
- **DebugX** — the WTL/ATL GUI app. `CMainFrame` has a WTLDock `CDockHost` as its client window; `CCommandView` is the one document pane (its output is a `CScintillaCtrl`, see below), and `COutputView`, `CCallStackView`, `CRegistersView`, `CModulesView`, `CBreakpointsView`, `CUserThreadsView`, `CUserProcessesView`, `CHandlesView`, `CKernelProcessesView`, `CKernelThreadsView`, `CDriversView`, `CObjectsView`, `CIrpsView`, `CMemoryView` (four of them: Memory, Memory 2-4, each with its own pane state), `CDisassemblyView`, `CLocalsView`, `CWatchView` are tool-window dock panes, described by the table in `PaneRegistry.cpp` (`PaneInfo`: stable id, title, icon, View-menu command, `Kind` — `Tool` docks around the documents, `Document` tabs in the central document area, which is what the Command view is —, default side and size, the target flags it `Requires`, `TabWith` — the pane whose group it joins the first time it is shown — and a maker). The list panes derive from `CListPane<T>` (`ListPane.h`: a virtual list plus `CPaneBase`, sorting, column-width persistence); a new one supplies `InitList`, `GetColumnText` and a `Refresh` coroutine ending in `RefreshDone()` then `UpdateList(count)`. `CListPane` also copies: Ctrl+C (`ID_EDIT_COPY`, which the frame's `OnForward` passes to the active pane) copies the selected rows as the list shows them, tab-separated, with a header line when there are several (an in-place editor with the focus gets `WM_COPY` instead); a pane without a right-click menu gets Copy / Copy All, and one with its own calls `AppendCopyItems(menu)` before `TrackPopupMenu` and `HandleCopyCommand(cmd)` after — a new menu should too. A list pane can also have a **filter box** above the list (`HasFilter()` true; Ctrl+F goes there — `CMainFrame::OnEditFind` sends `ID_EDIT_FIND` to a pane with no Scintilla —, Escape empties it): its `Refresh` calls `ApplyFilter(m_Items[, firstRow])` before `UpdateList`, which drops the rows whose cells (`GetColumnText`) lack the text, and a change to the text (300 ms after the last key, `FilterTimerId`) calls `FilterChanged()`, by default a refresh — a pane that keeps all of its rows filters them itself (Kernel Processes, through its `SortedFilteredVector`, without walking the kernel again). `CListPane` lays out the box and the list itself (`UpdateLayout`), and passes Ctrl+V/Ctrl+X (the frame's accelerators) to an edit of the pane's with the focus. A pane's `WM_TIMER` handler must leave other ids alone (`handled = FALSE`). Modules, Handles, Drivers, both Threads panes, Kernel Processes and Object Namespace have one. A pane is an `IPane` (`PaneBase.h`): it creates its own window, deletes itself in `OnFinalMessage`, and can `SaveState`/`LoadState` a string (the list panes keep their column widths; `PaneRegistry` collects these into `AppSettings::PaneStates`). A pane's window is created the first time the pane is shown (`SetContentFactory` → `PaneRegistry::CreatePane`), which is also how a restored layout brings back the panes that were open. Panes that show the target derive from `CPaneBase<T>`: session events only mark them dirty, and they refresh (`Refresh()`, a coroutine that ends with `RefreshDone()`) only when dirty, visible and `CanRefresh()` — so a hidden pane costs nothing while the target steps, and catches up when shown. The arrangement is saved to `%LOCALAPPDATA%\DebugX\layout.json` on close and restored at startup. **Layouts** (`DefaultLayouts.cpp`): there is a default for user mode and one for kernel mode, built by `BuildDefaultLayout` on a window-less `DockLayout` of its own (so only the panes it shows get windows, when it is loaded) — a new pane that belongs in a default goes there too. Each mode keeps its own layout: `CMainFrame::OnTargetAttached` switches to the other mode's (`SwitchLayoutMode`; the last one of each is in `mode-layouts.json`, the mode in use in `AppSettings::LayoutMode`), and `Window > Reset Window Layout` goes back to the current mode's default. `Window > Layouts` applies either default or a layout saved by name (`Save Layout As`, WTLDock's `DockLayoutStore`, in `layouts.json`; the submenu is made again in `WM_INITMENUPOPUP`). Layouts carry `LayoutVersion` (`DockLayout::SetAppVersion`); a `layout.json` of an older version is not restored — bump it when the defaults should replace what users have. The frame has a real menu (no command bar) whose icons come from `WTLHelper::InitMenu`, and two `ToolbarHelper` toolbars in a rebar, each a band: the debug commands, and the View menu's panes (`paneCommands` in `OnCreate`, icons from `PaneRegistry`; enabled like the menu items, by `UpdateUI`). A toolbar button's tooltip is its menu item's text (`OnToolTipText`), so a new button needs no string resource. **Dark mode** is WTLHelper's: `WTLHelper::InitDarkMode` runs in `_tWinMain` before any window exists (from `AppSettings::DarkMode`: 1 dark, 0 light, -1 follow the system; `AppSettings` is stored in `HKCU\Software\DebugX\Settings`), a per-thread hook then darkens every control and dialog as it is created, and `Options > Dark Mode` calls `WTLHelper::SwitchToMode`, which sends `WTLHelper::ThemeChangedMessage` to all descendants. What is drawn by the application itself follows the mode through that message: `CMainFrame::ApplyTheme` (dock theme, menu icons — they are bitmaps drawn on the menu's background) and `CCommandView::OnThemeChanged`/`ApplyOutputColors` (Scintilla style colors come from `GetSysColor`, which the library hooks to return the dark colors). New views should take colors from `GetSysColor` and handle that message rather than hard-code colors; likewise **fonts**: Options > Code Font / UI Font (`AppFonts.h`, saved in `AppSettings::CodeFont`/`UiFont` as `face;tenths of a point;weight;italic`, empty: Consolas / Segoe UI 9) — a view takes `AppFonts::CodeFont()` (monospace text; a Scintilla: `AppFonts::ApplyCodeFont` before its `StyleClearAll`) or `UiFont()` (its lists, edits, buttons; `CListPane` sets its list's) when created and again on `AppFonts::FontsChangedMessage` (wParam: which one), which `AppFonts::Choose` sends to the frame's descendants and to the windows it owns; a bar of controls sizes itself from the font (`AppFonts::TextHeight`). The dock's captions and tabs (fixed heights), menus, dialogs and the status bar keep the system's font; system file/folder pickers must be wrapped in `WTLHelper::SuspendHook()/ResumeHook()`. `DebugManager` is the process-wide singleton that owns the one debugger and the `SessionModel`: `DebugManager::Debugger()` is the `IDebugger` everything uses, `DbgEng()` the same object as a `DebuggerX*` (null for another engine), and `DebugManager::RunAsync` DbgEng's `RunAsync` (`E_NOTIMPL` otherwise), which the kernel panes use.

**Scintilla** (`ScintillaCtrl.h`/`.cpp`) is the editor control behind the Command view's output, the Disassembly view and the source documents. It is a plain Win32 control, not an ATL one: `Scintilla_RegisterClasses`/`Scintilla_ReleaseResources` (declared locally, not in any installed header) register/unregister its `"Scintilla"` window class once for the process, called from `_tWinMain` next to the RichEdit DLL load/free (RichEdit itself is no longer used anywhere in DebugX, but the DLL load stays for now in case a later view needs it). `CScintillaCtrl : CWindow` is the `TBase` for a `CContainedWindowT<CScintillaCtrl>`, exactly like `CRichEditCtrl`/`CListViewCtrl`; call `InitCall()` once right after `Create()` to bind its `Scintilla::ScintillaCall` (reached through `operator->()`, e.g. `m_Text->AppendText(...)`) to the control's direct-call function — no `SendMessage` round trip after that. The control is always `SC_CP_UTF8`; text in and out of the Scintilla API is `char` (UTF-8), so it goes through `ToUtf8`/`FromUtf8` (also in `ScintillaCtrl.h`) at the boundary with the rest of the app's wide strings. `DebugX/scintilla/ScintillaCall.cxx` is vendored, unmodified, upstream source (see `DebugX/scintilla/README.md`) — the vcpkg `scintilla` port builds the editor itself into `Scintilla.lib` but deliberately leaves this typed call layer as source for the consuming app to compile in, the same way SciTE does; its `AdditionalIncludeDirectories`/`PrecompiledHeader` overrides in `DebugX.vcxproj` are there because it is not part of the PCH and its quoted `#include`s need the vcpkg triplet's `scintilla` subdirectory specifically, not just the triplet's `include` root.
**Disassembly and Memory** are the other two Scintilla/HexControl-backed panes, both `CPaneBase<T>` (refresh only when dirty, visible and the target is stopped, like `CRegistersView`/`CCallStackView`, not the always-on-`OnOutput` pattern `CCommandView` uses). `CDisassemblyView` re-disassembles a fixed window of lines around the current instruction pointer on every refresh (`DebuggerX::Disassemble`, `GetInstructionOffset`) into its `CScintillaCtrl`, with an `::CreateLexer("asm")` Lexilla lexer (it ships with no instruction/register knowledge of its own — a mnemonic is plain `SCE_ASM_IDENTIFIER`, the default style, until `SetKeyWords` is given lists 0/1/2 (CPU/FPU instructions, registers), done once in `OnCreate`; `ApplyColors` then colors the resulting `SCE_ASM_*` styles from `SciLexer.h`, light/dark pairs redone on every theme change since `StyleClearAll` wipes them) and a symbol margin carrying two markers: a breakpoint circle (from `EnumBreakpoints`, clickable via `SCN_MARGINCLICK` to toggle one) and a current-line arrow. Its right-click menu has Toggle Breakpoint, Go to Address (to the address bar) and Run to Cursor (`RunTo(AddressLocation(address))`, DbgEng's `g <address>` — the engine's own one-shot run-to, not a breakpoint DebugX manages itself). `CMemoryView` reads a fixed-size chunk at an address *expression* (`DebuggerX::Evaluate`, e.g. `@$csp`, architecture-neutral for "current stack pointer") into a `CHexControl` (`wtlhelper/HexControl`) each refresh via a fresh `MemoryBuffer`; the expression — not just the address it last resolved to — is what's kept, so it re-evaluates (and so can track a moving register) on every stop. **Writing to the target.** `CMemoryView` hands `CHexControl` a `TargetMemoryBuffer` (`TargetMemoryBuffer.h`, an `IBufferManager`): in overwrite mode every edit the control makes (typing, paste, Delete — which zero-fills —, undo/redo) goes through `SetData`, which updates the local copy and calls `DebuggerX::WriteMemory`; `Insert`/`Delete` refuse (target memory has a fixed size) and the Insert key is swallowed by a `SetWindowSubclass` on the control so it never enters insert mode. It is editable only for a live target that is stopped. `WriteMemory` raises `MemoryChanged` (→ `ISessionObserver::OnMemoryChanged`) before its task completes, which is how the Memory pane tells its own writes (`m_PendingWrites`) from someone else's (`eb` in the Command view, also mapped to `MemoryChanged` from the engine's data-only `ChangeDebuggeeState`). `CRegistersView` edits a value in place (a hidden `CEdit` over the cell; double-click, F2, Enter) in frame 0 of a live target, through `DebuggerX::SetRegister` (`EvaluateWide` to the register's type for integers, `wcstod` for floating point, `E_NOTIMPL` for vectors).
**Scope frame, Locals and Watch.** Double-clicking a call-stack row calls `DebuggerX::SetScopeFrame` (`SetScopeFrameByIndex`); the engine's `DEBUG_CSS_SCOPE` symbol-state callback becomes a `ScopeChanged` notification and `ISessionObserver::OnScopeChanged`. Registers are read with `GetValues2(DEBUG_REGSRC_FRAME)` (so they follow the frame), the Disassembly view starts at the frame's instruction with a green marker, and the engine's own thread walk (`EnumProcesses`) saves and restores the scope frame, since `SetCurrentThreadId` resets it. `CLocalsView`/`CWatchView` share `CSymbolPane<T>` (`SymbolPane.h`): a tree flattened into a virtual list of `SymbolEntry` rows. Expansion is by *path* (names from the root, `'\n'`-separated), passed to `GetLocals`/`EvaluateWatches`, which walk the values afresh each time and expand the matching ones — so no row index is ever held across refreshes. The values are the **debugger data model's** (`DbgModel.h`, as `dx` shows them), not symbol groups: `GetLocals` is the keys of `@$curframe.Parameters` and `@$curframe.LocalVariables` (which follow the scope frame), a watch is `IDebugHostEvaluator2::EvaluateExtendedExpression` (C++ syntax; one that does not evaluate is an error object whose display string is the reason), and `ValueWalker` (`DebugEngine/ValueWalker.h`) turns them into rows: a type with a visualizer (NatVis — the Windows Kits debugger's `Visualizers` folder has the standard library's; System32's and the package's engines have none, and show the fields) by its keys (`[size]`, ...) and elements, with its fields under `[Raw View]`; another structure by its base classes and fields (static ones and constants left out, by `IDebugHostField::GetLocationKind`) with a `{X=1 Y=2}` summary; an array (or anything iterable) by its elements (at most `MaxElements`); a pointer by what it points to (a `char`/`wchar_t` pointer also shows its string). A row also has a C++ `Expression` (`point.X`, `array[1]`, `(*shape.Next).X`; none under a visualizer's keys) when it is a number, a pointer, ...: **editing a value** (`CSymbolPane`: double-click the Value column, F2 in Locals, Edit Value) is `DebuggerX::AssignValue`, which evaluates `(expression) = (value)` with the data model and raises `MemoryChanged`. Watch expressions are edited in place (`LVS_EDITLABELS`, last row adds one) and kept in the pane's saved state after `|e:`, tab-separated. In a source file, the mouse resting on a name (with what it is a member of: `a.b`, `p->b`, `this->b`) or in the selection shows its value in a call tip (`SCN_DWELLSTART`, `EvaluateWatches`) while the target is stopped.
**Source files.** Unlike the panes of `PaneRegistry`, source files are dock panes made on demand: one `PaneKind::Document` pane per file, id `"source:" + path`, owned by `SourceDocuments` (a member of `CMainFrame`, which wires it into the dock's content factory, `SetPaneFactory` — so the files open at the last run come back with the layout — and `OnPaneClosed`, which destroys a closed source pane's window and removes the pane). Where there is no source the status bar says why. `CSourceView` (`SourceView.h`) is a read-only Scintilla with the `"cpp"` Lexilla lexer (`lexer.cpp.track.preprocessor` off), line numbers and breakpoint markers it refreshes itself (`EnumBreakpoints` → `GetSourceLocations` of their offsets → its lines); it sets a breakpoint, and runs to a line (`g`), with the engine's `` `file:line` `` syntax, using the name the PDB has for the file when it is known (`SetSymbolFile`). F9 (Toggle Breakpoint, `ID_DEBUG_TOGGLEBREAKPOINT`: when a source document is the active pane `CMainFrame::OnDebugToggleBreakpoint` sends it `ID_DISASM_TOGGLEBREAKPOINT`; elsewhere it beeps — Ctrl+B, Add Breakpoint, is the dialog, everywhere) and Ctrl+F10 (`ID_DEBUG_RUNTOCURSOR`, which the frame's `OnForward` passes to the active pane) act on the caret's line, as do Ctrl+Shift+F10 (`ID_DEBUG_SETNEXTSTATEMENT`, Set Next Statement) and, in the Disassembly view, the same three on the caret's instruction. **Set Next Statement** is `DebugManager::SetNextStatement` → `DebuggerX::SetInstructionOffset` (the IP register by the effective processor type, then `ResetScope` and `ContextChanged`, as `SetRegister`); an address in another function than the IP's (by symbol start) is refused with `SetNextOtherFunction` unless forced, and the UI asks first. **Restart** (Ctrl+Shift+F5) is for a session started by Run Executable (`CMainFrame::m_Launch`, cleared by any other start): it saves the breakpoints, `Stop`s, launches again and sets them again, as any run does (see Saved breakpoints). **Saved breakpoints** (`SavedBreakpoints.h`, `%LOCALAPPDATA%\DebugX\breakpoints.txt`): each program's, by its executable's full path (lowercase; for an attach, `QueryFullProcessImageName` of the process), are set again when it is next run or attached to (`CMainFrame::RestoreBreakpoints`, which then sets `m_BreakpointsKey`), and saved on each `OnBreakpointsChanged` while the target is stopped — not while it runs or ends, when the engine removes them itself; `SaveBreakpoints` checks again after `EnumBreakpoints` returns, since the notice that the session ended comes first. Code breakpoints only, not one-shot ones, and by `BreakpointInfo::Location`, not by address: the expression a breakpoint was set with, else `` `file:line` `` where a line starts, else `module!function+0x10` (`EnumBreakpoints`; a `bp` typed in the Command view has no expression, only an address, which the next run does not have). **Find and Go To**: Edit > Find (Ctrl+F, `CFindDlg`), F3 / Shift+F3 search the active pane's Scintilla control — `CMainFrame::ActiveTextControl` takes the first visible one among the pane's child windows, so a new Scintilla-based view gets Find for nothing — with `FindInScintilla` (`FindDlg.h`; it goes round past the end, and the status bar says so). It sets the engine's code level (`SetCodeLevel`) for the one step and restores it, so `p`/`t` typed in the Command view are unaffected; it steps by instruction where the IP has no line information (a source-level `p` there would run on until it found some). A source-level `t` stops at whatever is called: Step Into follows jump thunks (incremental linking, imports), steps out of a function without lines (`gu`) and carries on with the line, so it ends in the next function that has source, or on the next line. **Paths**: `Options > Symbol and Source Paths` (`CSymbolPathsDlg`, an entry per line) edits the engine's paths (`GetSymbolPaths`/`SetSymbolPath`/`SetSourcePath`), saved in `AppSettings::SymbolPath`/`SourcePath` (empty: never set — `_NT_SYMBOL_PATH` and the like stand) and given to the engine at startup; `Debug > Reload Symbols` is `ReloadSymbols` (`.reload`, then `ContextChanged` so that the panes catch up). The engine is created with `SYMOPT_LOAD_LINES` (without it `` `file:line` `` still resolves, but warns "Line information loading disabled" each time).

The panes most used have WinDbg's shortcuts, Alt+1..7 (Command, Watch, Locals, Registers, Memory, Call Stack, Disassembly), and Alt+8/9/0 Threads, Modules, Breakpoints — not Visual Studio's Ctrl+Alt ones, which are AltGr characters on some keyboards (and would fire while typing in the Command view). Attach to Process lists the server's processes then (`EnumServerProcesses`, `CProcessSelectDlg::SetRemoteProcesses`); a remote program's breakpoints are not saved and it is not a recent target (its path is the other machine's), and `EnumHandles` is `E_NOTIMPL`. **Scripts** (Debug > Run / Load / Unload Script): `DebuggerX::Script` runs `.scriptrun` (which leaves the script loaded, like `.scriptload`), `.scriptload` or `.scriptunload` through `ExecuteCaptured` and repeats the output to everyone (the Command view); `EnumScripts` parses `.scriptlist`, leaving out the engine's own NatVis files. ## Architecture: threading model

DbgEng requires all calls to `IDebugClient`/`IDebugControl` etc. for a given client to happen on the thread that created the client. `DebuggerX::Impl` runs a **dedicated debug thread** (`DebuggerThread()`, started by `Create()`) that sleeps in an alertable wait; engine calls are queued onto it with `QueueUserAPC`. Because a call such as `g` keeps that thread inside `WaitForEvent` until the target breaks, a queued request simply waits its turn.

**The UI thread never blocks on the engine and never runs a nested message loop.** Every engine operation on `IDebugger` is a coroutine returning `DebugEngine::Task<T>`: it queues the work and suspends the caller; when the work is done the debug thread posts the coroutine's resumption through the `IDispatcher` given to `Create` (none: `CreateWindowDispatcher`'s message-only window on the calling, UI, thread), which resumes it there — so it works under any message loop, including modal dialogs. Notifications go through the same dispatcher, in order with the completions; what is still queued in it when the debugger shuts down is dropped. (A toolkit other than Win32's supplies a dispatcher of its own; the test runner wraps the window one in a counting one, so every suite goes through a dispatcher of the caller's.) Callers either `co_await` the task or just drop it (a dropped `Task` lets the coroutine finish and free itself; the result is discarded). Pointer/reference arguments (the out parameters of `Enum*`) must stay valid until the task completes; string arguments are copied. `IsBusy()` is true while any task is in flight. Only `Break()` (`SetInterrupt`) may be used from other threads; `Create()` and the destructor block briefly (the destructor interrupts a running target, detaches/ends the session on the debug thread and waits up to 5 s).

A coroutine can resume after the window that started it is gone. A window that starts coroutines keeps a `Lifetime` member (`Lifetime.h`) and each coroutine does `auto alive = m_Lifetime.Watch();` before its first `co_await` and `if (!*alive) co_return;` after every one, before touching the window. Anything the engine thread uses while a task runs must not belong to a window (see the shared `Enumeration` in `KernelProcessesView`).

Engine events (breakpoints, exceptions, thread/process create/exit, output text, execution-status changes) arrive on `IDebugEventCallbacks`/`IDebugOutputCallbacks2` implemented by `Impl` itself, on the debug thread. They are queued under a mutex (with a single coalesced wake-up message, so a flood of output cannot overflow the message queue) and delivered on the UI thread to the `NotificationHandler` passed to `Create()`. The data pointer is only valid during the call — the debugger frees it afterwards, receivers never do. `DebugManager` passes them to the `SessionModel` (`SessionModel.h`), which turns them into typed events for the `ISessionObserver`s registered with `AddObserver`/`RemoveObserver` (windows add themselves when created and remove themselves in `WM_DESTROY`): `OnSessionChanged` (status, busy or target changed — re-derive your controls from `Session()`), `OnBroke`/`OnResumed`, `OnContextChanged` (the current thread changed, or the target broke), `OnScopeChanged` (another frame of the current thread's stack was chosen — `SessionModel::CurrentFrame()`; stops and thread changes reset it to 0 without this event), `OnBreakpointsChanged`, `OnModuleLoaded`/`Unloaded`, `OnTargetAttached`/`OnTargetEnded`, `OnThreadCreated`/`Exited`, `OnProcessCreated`/`Exited`, `OnOutput`, `OnLogLine` (the bounded event log the Output pane shows). It all runs on the UI thread, so there is no locking and no cross-thread `SendMessage`. The engine adds two payload-free notifications for state a caller can otherwise only poll: `BusyChanged` (a call went in flight / the last one completed) and `TargetChanged` (attached, opened, or — when the status becomes NoDebuggee — ended, which resets `GetTargetType()` to Unknown). The execution status is tracked from `StatusChanged` payloads (in order with the other events), not read from the engine.

`Impl` is a COM object whose references are held by the engine (as its callbacks); the engine lets go of them on the debug thread when the client is released. `DebuggerX` therefore holds a reference of its own and releases it only after the shutdown request has run — do not `delete` the object.

## Conventions to know

- Generic UI helpers come from WTLHelper, not from local copies: `CVirtualListView<T>` (virtual list views; callbacks are `GetColumnText(HWND, row, col)`, `GetRowImage(HWND, row, col)`, `DoSort(const SortInfo*)`), `SortedFilteredVector<T>` (STL-style names: `push_back`, `clear`, `size` = filtered size), `SortHelper::Sort`, `CDialogHelper<T>` (`AdjustOKCancelButtons(okIcon, cancelIcon)`, `AddIconToButton`), `SecurityHelper`, `IconHelper`, `ToolbarHelper`. DebugX's include path has `wtlhelper/WTLHelper`, so `#include "SortHelper.h"` etc. resolve there; add a helper to WTLHelper rather than to DebugX when it is not DebugX-specific.

- `TargetType` is a flags enum (`DEFINE_ENUM_FLAG_OPERATORS`) — check kernel vs. user targets with bitwise `&` (e.g. `GetTargetType() & TargetType::Kernel`), not equality.
- The `HR(x)` macro (defined locally in each `.cpp` that uses it) early-returns the enclosing function on a failed `HRESULT` — it assumes the enclosing lambda/function returns `HRESULT`. Use it inside the lambdas that run on the debug thread, not in a coroutine body (`return` is not allowed there).
- The UI state of the toolbar/menus (`CMainFrame::UpdateUI`, which also enables each View-menu pane command from its `PaneInfo::Requires`) and of the Command view is derived from `DebugManager::Session()` in `OnSessionChanged`; nothing polls, and nothing else sets it. A new pane goes in the `PaneRegistry` table *and* needs its own `COMMAND_ID_HANDLER(ID_VIEW_x, OnViewPane)` line in `CMainFrame`'s message map — `MainFrm.h`'s trailing `COMMAND_RANGE_HANDLER(0x8000, 0xffff, OnForward)` silently swallows a `ID_VIEW_*`/other menu command in that range that has no handler of its own, so a forgotten line looks like the menu item does nothing, not like a build or runtime error. Observer member names must not collide with the mixed-in classes' (`CVirtualListView` has its own `OnStateChanged`, `CWindow` has `Invalidate`).
- A `BS_FLAT` button made in code draws its own frame: no `WS_BORDER` (that is a second one). A pane (a `CFrameWindowImpl`) that hosts buttons or leaves gaps between its controls chains `CThemedBackground<T>` (`ThemedBackground.h`): its class brush is `COLOR_WINDOW + 1`, which user32 resolves inside `DefWindowProc` past WTLHelper's color hooks, so its background is white in dark mode -- around a themed button too, which paints its corners with its parent's background. A pane that lays out an edit (a multiline one especially) next to other controls repaints them all after it moves them (`RedrawWindow(... RDW_ALLCHILDREN)`, as `CAssistantView::OnSize` does), or the edit shows what was there before.
- Pitfalls found in the panes: a virtual list (`LVS_OWNERDATA`) never notifies a check box toggle — hit-test in `OnListViewClick` (`LVHT_ONITEMSTATEICON`); `CListViewCtrl::GetSelectedIndex` asserts unless `LVS_SINGLESEL` (use `GetNextItem(-1, LVNI_SELECTED)`); `CVirtualListView`'s double/right click handlers use `GetCursorPos`; `IDebugControl::RemoveBreakpoint2` frees the breakpoint, so `Detach()` the `CComPtr` before calling it (a Release afterwards is a use-after-free on the debug thread).
- Debug commands also come from accelerators (F5, F10, F11, Ctrl+Break, ...), and `CUpdateUI` only brings a menu item's enabled state up to date when its popup opens — so a command handler must check `DebugManager::Session()` itself (`CanRun()`, `CMainFrame::CanStartSession()`) rather than rely on `UIEnable` having grayed it out.
- WTLHelper's `Settings::Set<T>` does not update the stored `Size`, so a setting must be read and written with the same type it was declared with in `BEGIN_SETTINGS` (a `SettingType::Bool` declared with `1` is 4 bytes; writing a `bool` to it overruns on save) — declare on/off settings as `Int32` and use `int`, as `DarkMode`/`Dml` do.
- Scintilla pitfalls: unlike RichEdit's `AppendText`, `SCI_APPENDTEXT` (`ScintillaCall::AppendText`) still checks `SCI_SETREADONLY` (`Document::InsertString` does the check) — a read-only log view has to toggle it off/on around its own appends, see `CCommandView::AppendText`. A DML/hyperlink-style run is a Scintilla *hotspot* style (`StyleSetHotSpot`), not manual hit-testing: style the run, catch `SCN_HOTSPOTCLICK`'s `NotificationData::position` (a byte offset — the control is UTF-8) instead of chasing `WM_SETCURSOR`/`CharFromPos`. `GenericEditCommands.h`'s Select All/Clear All special-case a focused window whose class name contains "Scintilla" (it is ATL-superclassed to `"ATL:Scintilla"`, never checked as an exact match) to send `SCI_SETSEL`/`SCI_CLEARALL` instead of the `CEdit`-style calls that plain `EM_*` messages need. Scintilla does not send `NM_RCLICK`; a pane's own right-click menu is a `WM_CONTEXTMENU` handler on the contained window's `ALT_MSG_MAP`, as `CDisassemblyView` does.
- `CHexControl` (`wtlhelper/HexControl`) is built on `CBufferedPaintWindowImpl`, from `<atltheme.h>` — not part of `pch.h`'s own include chain, so a view that uses it (`MemoryView.h`) includes it explicitly before `SimpleHexControl.h`, or every method the base class should have supplied errors out as if `CHexControl` had no base class at all.
- Breakpoints: `DebuggerX::AddBreakpoint`/`UpdateBreakpoint` take a `BreakpointSettings` (code or data, condition, command, pass count, thread, one-shot, enabled); `CBreakpointDlg` edits one. The engine has no breakpoint conditions: DebugX keeps the condition (and a hit count) itself, keyed by `IDebugBreakpoint3::GetGuid` — not by id, which the engine reuses, also after a `bc` typed in the Command view — and evaluates it as `@@c++(...)` in the `Breakpoint` event callback, returning `DEBUG_STATUS_GO` when it is zero (the engine then does not run the breakpoint's command either); a condition that does not evaluate breaks. `IDebugBreakpoint2` does not derive from `IDebugBreakpoint`, so helpers that take either use `IUnknown*`. A breakpoint on a function name is on its first instruction, before the prologue: a condition on its *arguments* reads them before they are where the PDB says (see the symbol group note below) and does not evaluate, so it breaks every time — a source line (`` `file.cpp:N` ``) or an address inside the body works. Data breakpoints are evaluated to an address once (`SetOffset`), must be aligned to their size (1/2/4/8), and cannot change type on update (`E_INVALIDARG`).
- Exceptions and events: whether one breaks is the engine's event filters' decision (`DebuggerX::GetEventFilters`/`SetEventFilters`, edited by `CExceptionSettingsDlg`, Debug > Exception Settings); `Impl::Exception` returns `DEBUG_STATUS_NO_CHANGE` and only reports the exception (`ExceptionData`, logged to the Output pane) — a callback that returns `DEBUG_STATUS_BREAK` overrides the user's choice. Specific events are matched by name, exceptions by code (one the engine has no filter for is added; `SetEventFilters` removes the added ones not in the list it is given); the filter with code 0 is the engine's "Unknown exception", the policy for every code without its own. The defaults are captured when the engine is created (`GetEventFilters(..., true)`); only the differences from them are saved (`AppSettings::EventFilters`, `EventFilterText`) and re-applied at startup, so a newer engine's defaults still hold for the rest. The filters belong to the engine, not to a session: they carry over from one target to the next.
- `GetValues2(DEBUG_REGSRC_FRAME)` (and the symbol groups) read the *scope's* copy of the register context, which `IDebugRegisters::SetValue` does not update — `SetRegister` calls `ResetScope()` afterwards, or the Registers pane shows the old value. A data-only `ChangeDebuggeeState` also arrives while a step is executing, so it means "memory was written" only when the status is `DEBUG_STATUS_BREAK`.
- **Which dbgeng.dll.** `DebugX.exe` delay-loads it, and `DebugManager::Init` picks it before the engine is created (`DebugEngine::LoadEngine(EngineSource::Automatic)`, `EngineLoader.cpp`): the Windows Kits debugger's (`WindowsKitsDebuggersFolder`: `...\Windows Kits\10\Debuggers\<arch>\`, from the registry's Installed Roots, else the default install folder), loaded with `LOAD_WITH_ALTERED_SEARCH_PATH` so its own `dbghelp.dll`, `symsrv.dll` and extension DLLs come with it; else System32's. The status bar says which at startup. The NuGet package's DLLs (`DebugEngine/amd64`) are not used by the app (only by the tests). System32's differs from the others: its `IDebugSymbols5::GetCurrentScopeFrameIndex` fails (`E_OUTOFMEMORY`) for any frame, so the scope frame's index is read through `Impl::GetScopeFrameIndex`, which falls back to `GetScope`'s `DEBUG_STACK_FRAME::FrameNumber`. Also, at the initial break it has loaded no symbols, and a `` `file:line` `` (a breakpoint, `g`) is looked up only in loaded ones — it becomes a deferred breakpoint that never hits — so `LaunchAndAttach`/`AttachToProcess` load the executable's symbols there (`Impl::LoadExecutableSymbols`, `.reload /f <exe>`). Test engine changes against both DLLs (`DebugEngineTests` does, see Build). **System32's and the package's engines have no `symsrv.dll` and no extension DLLs** (`ext`, `exts`, `uext`, `kdexts`, ...; only the Windows Kits debugger has them — which is why it is preferred): `srv*` elements of the symbol path are ignored (`DBGHELP: x.pdb - file not found`, no `SYMSRV` lines with `!sym noisy`) — only a PDB the image points to, or one in a plain folder, loads; Windows' own modules, and the kernel, get export symbols only — and every `!`-command fails. `symsrv.dll` is looked for next to the `dbghelp.dll` the engine uses (the application's folder does not do for System32's). The engine's own breakpoints (the one `gu` or `g <address>` runs to) also come to the `Breakpoint` callback; they are not in its list (`GetBreakpointById` fails for their id).
- Building one project on its own (`MSBuild DebugEngine.vcxproj`) puts its output somewhere other than the solution build does (`$(SolutionDir)` is not set); build `DebugX.sln`.
- Data model: `IModelObject::EnumerateRawValues` on a synthetic object (`@$curframe.LocalVariables`) crashes inside `dbgmodel.dll` — call it on `ObjectTargetObject`s only. Every object has method keys (`Where`, `Select`, `ToDisplayString`, ...): skip `ObjectMethod` values. A native number or pointer is an `ObjectIntrinsic` with no location (`GetLocation` fails), so it is assigned through an expression, not written to memory. At a breakpoint on a function's first instruction, a debug build's locals and arguments read `<Memory access error>`: they are addressed from a frame register the prologue has not set up yet; that is not a DebugX bug.
- Kernel process/thread walking (`DebugX.Kernel`) reads target memory/symbols directly (e.g. `_EPROCESS` linked lists) rather than using `IDebugSystemObjects`, since that API only works for live user-mode/live-kernel targets, not always applicable — check `KernelAnalyzerBase`/`KernelGlobals` before assuming a helper works for dumps.
