# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

DebugX is a Windows-only GUI/CLI debugger front-end built on top of the Windows Debug Engine (DbgEng/`IDebugClient` COM APIs — `DbgEng.h`/`DbgModel.h`). It wraps `dbgeng.dll` to attach to live user-mode processes, launch executables under the debugger, open crash dumps, and attach to a local kernel debugger, then exposes process/thread/module enumeration and command execution to a WTL-based docking GUI.

## Build

This is a Visual Studio solution (`DebugX.sln`) with six C++ projects, built via MSBuild/Visual Studio (not the top-level `CMakeLists.txt` — that file only builds an unrelated `Project1` ImGui scratch/demo app and references a `Test2` subdirectory that does not exist in this repo; ignore it unless working specifically on the ImGui experiment).

WTL and the docking framework come from the `wtlhelper` git submodule (`git submodule update --init`): `wtlhelper/WTL` is the WTL 10.01 that every project compiles against, and `wtlhelper/WTLDock/WTLDock.vcxproj` (a static library, part of `DebugX.sln`) is the docking framework — see `wtlhelper/WTLDock/README.md` for its API — and `wtlhelper/WTLHelper/WTLHelper.vcxproj` (also part of the solution) is the helper library that provides dark mode, the toolbar builder, menu icons and the settings store. WTLHelper needs Detours and WIL from **vcpkg** (the static triplets: `vcpkg install detours wil scintilla lexilla --triplet x64-windows-static`, and `x86-windows-static` for x86; vcpkg's user-wide MSBuild integration must be on). `DebugX.vcxproj` sets `VcpkgUseStatic` so it links the static-CRT builds. Remaining dependencies are restored via NuGet (`packages.config` per project): WIL (`Microsoft.Windows.ImplementationLibrary`) and `Microsoft.Debugging.DataModel.CppLib` / `Microsoft.Debugging.Platform.DbgEng` (DbgEng headers/import libs). Open `DebugX.sln` in Visual Studio and build/run normally, or use MSBuild (`MSBuild.exe DebugX.sln -p:Configuration=Debug -p:Platform=x64`); all four x86/x64 Debug/Release configurations build. There is no test suite in this repo.

## Projects

- **DebugEngine** (static lib) — the core wrapper around DbgEng. `Debugger.h`/`.cpp` defines `DebugEngine::DebuggerX`, the pImpl-based public API (`DebuggerX::Impl`) that owns the `IDebugClient7`/`IDebugControl7`/etc. COM pointers. `AsyncTask.h` is the coroutine `Task<T>` its calls return.
- **DebugX.Kernel** (static lib) — kernel-mode analysis helpers used when attached to a live/local kernel target (`DebugX::Analysis` namespace): `KernelGlobals` (symbol/global lookup), `KernelProcessAnalyzer`/`KernelProcessEnumerator` (walks `_EPROCESS` via the debugger's symbol/data-space APIs), `KernelThreadAnalyzer`/`KernelProcessThreadEnumerator`. These are plain analysis classes, not an actual kernel driver, despite the project name.
- **DebugX** — the WTL/ATL GUI app. `CMainFrame` has a WTLDock `CDockHost` as its client window; the tool windows (`CCommandView`, `COutputView`, `CCallStackView`, `CRegistersView`, `CModulesView`, `CBreakpointsView`, `CUserThreadsView`, `CKernelProcessesView`) are dock panes described by the table in `PaneRegistry.cpp` (`PaneInfo`: stable id, title, icon, View-menu command, `Kind` — `Tool` docks around the documents, `Document` tabs in the central document area, which is what the Command view is —, default side and size, the target flags it `Requires`, `TabWith` — the pane whose group it joins the first time it is shown — and a maker). The list panes derive from `CListPane<T>` (`ListPane.h`: a virtual list plus `CPaneBase`, sorting, column-width persistence); a new one supplies `InitList`, `GetColumnText` and a `Refresh` coroutine ending in `RefreshDone()` then `UpdateList(count)`. A pane is an `IPane` (`PaneBase.h`): it creates its own window, deletes itself in `OnFinalMessage`, and can `SaveState`/`LoadState` a string (the list panes keep their column widths; `PaneRegistry` collects these into `AppSettings::PaneStates`). A pane's window is created the first time the pane is shown (`SetContentFactory` → `PaneRegistry::CreatePane`), which is also how a restored layout brings back the panes that were open. Panes that show the target derive from `CPaneBase<T>`: session events only mark them dirty, and they refresh (`Refresh()`, a coroutine that ends with `RefreshDone()`) only when dirty, visible and `CanRefresh()` — so a hidden pane costs nothing while the target steps, and catches up when shown. The arrangement is saved to `%LOCALAPPDATA%\DebugX\layout.json` on close and restored at startup (`Window > Reset Window Layout` goes back to the default). The frame has a real menu (no command bar) whose icons come from `WTLHelper::InitMenu`, and a `ToolbarHelper` toolbar in a rebar. **Dark mode** is WTLHelper's: `WTLHelper::InitDarkMode` runs in `_tWinMain` before any window exists (from `AppSettings::DarkMode`: 1 dark, 0 light, -1 follow the system; `AppSettings` is stored in `HKCU\Software\DebugX\Settings`), a per-thread hook then darkens every control and dialog as it is created, and `Options > Dark Mode` calls `WTLHelper::SwitchToMode`, which sends `WTLHelper::ThemeChangedMessage` to all descendants. What is drawn by the application itself follows the mode through that message: `CMainFrame::ApplyTheme` (dock theme, menu icons — they are bitmaps drawn on the menu's background) and `CCommandView::OnThemeChanged` (rich edit colors come from `GetSysColor`, which the library hooks to return the dark colors). New views should take colors from `GetSysColor` and handle that message rather than hard-code colors; system file/folder pickers must be wrapped in `WTLHelper::SuspendHook()/ResumeHook()`. `DebugManager` is the process-wide singleton that owns the one `DebuggerX` and the `SessionModel`.
- **CDebugX** — a standalone console test/reference harness (`wmain`) that drives DbgEng directly (bypassing `DebuggerX`) to attach by PID, open a dump, or attach to the local kernel and run an interactive command loop. Useful as a minimal reference for DbgEng call sequences; it only borrows the notification data structs from `Debugger.h`.

Also present: `hello_imgui` and `imgui_bundle` git submodules (pulled in for the unrelated `Project1` ImGui experiment, not part of the debugger itself).

## Architecture: threading model

DbgEng requires all calls to `IDebugClient`/`IDebugControl` etc. for a given client to happen on the thread that created the client. `DebuggerX::Impl` runs a **dedicated debug thread** (`DebuggerThread()`, started by `Create()`) that sleeps in an alertable wait; engine calls are queued onto it with `QueueUserAPC`. Because a call such as `g` keeps that thread inside `WaitForEvent` until the target breaks, a queued request simply waits its turn.

**The UI thread never blocks on the engine and never runs a nested message loop.** Every engine operation on `DebuggerX` is a coroutine returning `DebugEngine::Task<T>`: it queues the work and suspends the caller; when the work is done the debug thread posts a message to a message-only window that `DebuggerX` creates on the calling (UI) thread, and that window resumes the coroutine there — so it works under any message loop, including modal dialogs. Callers either `co_await` the task or just drop it (a dropped `Task` lets the coroutine finish and free itself; the result is discarded). Pointer/reference arguments (the out parameters of `Enum*`) must stay valid until the task completes; string arguments are copied. `IsBusy()` is true while any task is in flight. Only `Break()` (`SetInterrupt`) may be used from other threads; `Create()` and the destructor block briefly (the destructor interrupts a running target, detaches/ends the session on the debug thread and waits up to 5 s).

A coroutine can resume after the window that started it is gone. A window that starts coroutines keeps a `Lifetime` member (`Lifetime.h`) and each coroutine does `auto alive = m_Lifetime.Watch();` before its first `co_await` and `if (!*alive) co_return;` after every one, before touching the window. Anything the engine thread uses while a task runs must not belong to a window (see the shared `Enumeration` in `KernelProcessesView`).

Engine events (breakpoints, exceptions, thread/process create/exit, output text, execution-status changes) arrive on `IDebugEventCallbacks`/`IDebugOutputCallbacks2` implemented by `Impl` itself, on the debug thread. They are queued under a mutex (with a single coalesced wake-up message, so a flood of output cannot overflow the message queue) and delivered on the UI thread to the `NotificationHandler` passed to `Create()`. The data pointer is only valid during the call — the debugger frees it afterwards, receivers never do. `DebugManager` passes them to the `SessionModel` (`SessionModel.h`), which turns them into typed events for the `ISessionObserver`s registered with `AddObserver`/`RemoveObserver` (windows add themselves when created and remove themselves in `WM_DESTROY`): `OnSessionChanged` (status, busy or target changed — re-derive your controls from `Session()`), `OnBroke`/`OnResumed`, `OnContextChanged` (the current thread changed, or the target broke), `OnBreakpointsChanged`, `OnModuleLoaded`/`Unloaded`, `OnTargetAttached`/`OnTargetEnded`, `OnThreadCreated`/`Exited`, `OnProcessCreated`/`Exited`, `OnOutput`, `OnLogLine` (the bounded event log the Output pane shows). It all runs on the UI thread, so there is no locking and no cross-thread `SendMessage`. The engine adds two payload-free notifications for state a caller can otherwise only poll: `BusyChanged` (a call went in flight / the last one completed) and `TargetChanged` (attached, opened, or — when the status becomes NoDebuggee — ended, which resets `GetTargetType()` to Unknown). The execution status is tracked from `StatusChanged` payloads (in order with the other events), not read from the engine.

`Impl` is a COM object whose references are held by the engine (as its callbacks); the engine lets go of them on the debug thread when the client is released. `DebuggerX` therefore holds a reference of its own and releases it only after the shutdown request has run — do not `delete` the object.

## Conventions to know

- Generic UI helpers come from WTLHelper, not from local copies: `CVirtualListView<T>` (virtual list views; callbacks are `GetColumnText(HWND, row, col)`, `GetRowImage(HWND, row, col)`, `DoSort(const SortInfo*)`), `SortedFilteredVector<T>` (STL-style names: `push_back`, `clear`, `size` = filtered size), `SortHelper::Sort`, `CDialogHelper<T>` (`AdjustOKCancelButtons(okIcon, cancelIcon)`, `AddIconToButton`), `SecurityHelper`, `IconHelper`, `ToolbarHelper`. DebugX's include path has `wtlhelper/WTLHelper`, so `#include "SortHelper.h"` etc. resolve there; add a helper to WTLHelper rather than to DebugX when it is not DebugX-specific.

- `TargetType` is a flags enum (`DEFINE_ENUM_FLAG_OPERATORS`) — check kernel vs. user targets with bitwise `&` (e.g. `GetTargetType() & TargetType::Kernel`), not equality.
- The `HR(x)` macro (defined locally in each `.cpp` that uses it) early-returns the enclosing function on a failed `HRESULT` — it assumes the enclosing lambda/function returns `HRESULT`. Use it inside the lambdas that run on the debug thread, not in a coroutine body (`return` is not allowed there).
- The UI state of the toolbar/menus (`CMainFrame::UpdateUI`, which also enables each View-menu pane command from its `PaneInfo::Requires`) and of the Command view is derived from `DebugManager::Session()` in `OnSessionChanged`; nothing polls, and nothing else sets it. A new pane goes in the `PaneRegistry` table; observer member names must not collide with the mixed-in classes' (`CVirtualListView` has its own `OnStateChanged`, `CWindow` has `Invalidate`).
- Pitfalls found in the panes: a virtual list (`LVS_OWNERDATA`) never notifies a check box toggle — hit-test in `OnListViewClick` (`LVHT_ONITEMSTATEICON`); `CListViewCtrl::GetSelectedIndex` asserts unless `LVS_SINGLESEL` (use `GetNextItem(-1, LVNI_SELECTED)`); `CVirtualListView`'s double/right click handlers use `GetCursorPos`; `IDebugControl::RemoveBreakpoint2` frees the breakpoint, so `Detach()` the `CComPtr` before calling it (a Release afterwards is a use-after-free on the debug thread).
- Kernel process/thread walking (`DebugX.Kernel`) reads target memory/symbols directly (e.g. `_EPROCESS` linked lists) rather than using `IDebugSystemObjects`, since that API only works for live user-mode/live-kernel targets, not always applicable — check `KernelAnalyzerBase`/`KernelGlobals` before assuming a helper works for dumps.
