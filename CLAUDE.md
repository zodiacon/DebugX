# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

DebugX is a Windows-only GUI/CLI debugger front-end built on top of the Windows Debug Engine (DbgEng/`IDebugClient` COM APIs — `DbgEng.h`/`DbgModel.h`). It wraps `dbgeng.dll` to attach to live user-mode processes, launch executables under the debugger, open crash dumps, and attach to a local kernel debugger, then exposes process/thread/module enumeration and command execution to a WTL-based docking GUI.

## Build

This is a Visual Studio solution (`DebugX.sln`) with seven C++ projects (and, in its Tests folder, a test runner and four programs it debugs), built via MSBuild/Visual Studio (not the top-level `CMakeLists.txt` — that file only builds an unrelated `Project1` ImGui scratch/demo app and references a `Test2` subdirectory that does not exist in this repo; ignore it unless working specifically on the ImGui experiment).

WTL and the docking framework come from the `wtlhelper` git submodule (`git submodule update --init`): `wtlhelper/WTL` is the WTL 10.01 that every project compiles against, and `wtlhelper/WTLDock/WTLDock.vcxproj` (a static library, part of `DebugX.sln`) is the docking framework — see `wtlhelper/WTLDock/README.md` for its API — and `wtlhelper/WTLHelper/WTLHelper.vcxproj` (also part of the solution) is the helper library that provides dark mode, the toolbar builder, menu icons and the settings store. WTLHelper needs Detours and WIL from **vcpkg** (the static triplets); DebugX itself needs Scintilla and Lexilla (the Command view's output, and the Disassembly view's): `vcpkg install detours wil scintilla lexilla --triplet x64-windows-static`, and again for `x86-windows-static`. vcpkg's user-wide MSBuild integration must be on. `wtlhelper/HexControl` (behind the Memory view; also part of `DebugX.sln`, see below) needs nothing beyond `wtlhelper/WTL`. `DebugX.vcxproj` sets `VcpkgUseStatic` so it links the static-CRT builds. Remaining dependencies are restored via NuGet (`packages.config` per project): WIL (`Microsoft.Windows.ImplementationLibrary`) and `Microsoft.Debugging.DataModel.CppLib` / `Microsoft.Debugging.Platform.DbgEng` (DbgEng headers/import libs). Open `DebugX.sln` in Visual Studio and build/run normally, or use MSBuild (`MSBuild.exe DebugX.sln -p:Configuration=Debug -p:Platform=x64`); all four x86/x64 Debug/Release configurations build.

**Tests.** `Tests\DebugEngineTests` (x64 only, in the solution's Tests folder) tests `DebugEngine::DebuggerX` against small programs it debugs, `Tests\Targets\{loop,src,exc,scope,values,procs}` (projects `TestTarget.x`, built as `x64\<configuration>\Tests\x.exe` — always unoptimized debug builds with incremental linking, see `Target.props`; the tests depend on their line numbers and function names). Run `x64\Debug\DebugEngineTests.exe` after building the solution: with no arguments it runs every suite (`scope`, `bp`, `exc`, `src`, `next`, `dump`, `values`, `procs`, `kernel` — the last attaches to the local kernel and looks at the runner's own process; it needs an elevated runner, `bcdedit /debug on` and the kernel's symbols, and says SKIP without them) once with each `dbgeng.dll` — the Windows Kits debugger's (if installed; what `DebugX.exe` loads then), System32's (what it loads otherwise) and the NuGet package's (`DebugEngine\amd64`) — since they behave differently (it is delay-loaded and chosen with `DebugEngine::LoadEngine`; `--engine kits|system|package` picks one, suite names pick suites). The `kernel` suite runs fully only on the Kits engine (the others have no `symsrv.dll` for the kernel's symbols; System32's may also refuse the local kernel once a newer engine has loaded its kernel debugging driver); the exit code is the number of failed checks; with `DEBUGENGINETESTS_OUTPUT=1` in the environment it also prints the engine's output. Each suite is a coroutine on the runner's message loop with a `DebuggerX` of its own, as DebugX's windows use it. A change to the engine is not done until both engines pass; there are no UI tests.

## Projects

- **DebugEngine** (static lib) — the core wrapper around DbgEng. `Debugger.h`/`.cpp` defines `DebugEngine::DebuggerX`, the pImpl-based public API (`DebuggerX::Impl`) that owns the `IDebugClient7`/`IDebugControl7`/etc. COM pointers. `AsyncTask.h` is the coroutine `Task<T>` its calls return.
- **DebugX.Kernel** (static lib) — kernel-mode analysis helpers used when attached to a live/local kernel target (`DebugX::Analysis` namespace): `KernelGlobals` (symbol/global lookup), `KernelProcessAnalyzer`/`KernelProcessEnumerator` (walks `_EPROCESS` via the debugger's symbol/data-space APIs), `KernelThreadAnalyzer`/`KernelProcessThreadEnumerator`, `KernelObjectAnalyzer` (the object manager's namespace from `ObpRootDirectoryObject`, an object's type through `ObTypeIndexTable`/`ObHeaderCookie` and its name through `ObpInfoMaskToOffset`; the driver objects of `\Driver` and `\FileSystem`; a thread's pending IRPs from `_ETHREAD.IrpList`). It is built as C++17. These are plain analysis classes, not an actual kernel driver, despite the project name.
- **DebugX** — the WTL/ATL GUI app. `CMainFrame` has a WTLDock `CDockHost` as its client window; `CCommandView` is the one document pane (its output is a `CScintillaCtrl`, see below), and `COutputView`, `CCallStackView`, `CRegistersView`, `CModulesView`, `CBreakpointsView`, `CUserThreadsView`, `CUserProcessesView`, `CHandlesView`, `CKernelProcessesView`, `CKernelThreadsView`, `CDriversView`, `CObjectsView`, `CIrpsView`, `CMemoryView` (four of them: Memory, Memory 2-4, each with its own pane state), `CDisassemblyView`, `CLocalsView`, `CWatchView` are tool-window dock panes, described by the table in `PaneRegistry.cpp` (`PaneInfo`: stable id, title, icon, View-menu command, `Kind` — `Tool` docks around the documents, `Document` tabs in the central document area, which is what the Command view is —, default side and size, the target flags it `Requires`, `TabWith` — the pane whose group it joins the first time it is shown — and a maker). The list panes derive from `CListPane<T>` (`ListPane.h`: a virtual list plus `CPaneBase`, sorting, column-width persistence); a new one supplies `InitList`, `GetColumnText` and a `Refresh` coroutine ending in `RefreshDone()` then `UpdateList(count)`. A pane is an `IPane` (`PaneBase.h`): it creates its own window, deletes itself in `OnFinalMessage`, and can `SaveState`/`LoadState` a string (the list panes keep their column widths; `PaneRegistry` collects these into `AppSettings::PaneStates`). A pane's window is created the first time the pane is shown (`SetContentFactory` → `PaneRegistry::CreatePane`), which is also how a restored layout brings back the panes that were open. Panes that show the target derive from `CPaneBase<T>`: session events only mark them dirty, and they refresh (`Refresh()`, a coroutine that ends with `RefreshDone()`) only when dirty, visible and `CanRefresh()` — so a hidden pane costs nothing while the target steps, and catches up when shown. The arrangement is saved to `%LOCALAPPDATA%\DebugX\layout.json` on close and restored at startup (`Window > Reset Window Layout` goes back to the default). The frame has a real menu (no command bar) whose icons come from `WTLHelper::InitMenu`, and a `ToolbarHelper` toolbar in a rebar. **Dark mode** is WTLHelper's: `WTLHelper::InitDarkMode` runs in `_tWinMain` before any window exists (from `AppSettings::DarkMode`: 1 dark, 0 light, -1 follow the system; `AppSettings` is stored in `HKCU\Software\DebugX\Settings`), a per-thread hook then darkens every control and dialog as it is created, and `Options > Dark Mode` calls `WTLHelper::SwitchToMode`, which sends `WTLHelper::ThemeChangedMessage` to all descendants. What is drawn by the application itself follows the mode through that message: `CMainFrame::ApplyTheme` (dock theme, menu icons — they are bitmaps drawn on the menu's background) and `CCommandView::OnThemeChanged`/`ApplyOutputColors` (Scintilla style colors come from `GetSysColor`, which the library hooks to return the dark colors). New views should take colors from `GetSysColor` and handle that message rather than hard-code colors; system file/folder pickers must be wrapped in `WTLHelper::SuspendHook()/ResumeHook()`. `DebugManager` is the process-wide singleton that owns the one `DebuggerX` and the `SessionModel`.

**Scintilla** (`ScintillaCtrl.h`/`.cpp`) is the editor control behind the Command view's output, the Disassembly view and the source documents. It is a plain Win32 control, not an ATL one: `Scintilla_RegisterClasses`/`Scintilla_ReleaseResources` (declared locally, not in any installed header) register/unregister its `"Scintilla"` window class once for the process, called from `_tWinMain` next to the RichEdit DLL load/free (RichEdit itself is no longer used anywhere in DebugX, but the DLL load stays for now in case a later view needs it). `CScintillaCtrl : CWindow` is the `TBase` for a `CContainedWindowT<CScintillaCtrl>`, exactly like `CRichEditCtrl`/`CListViewCtrl`; call `InitCall()` once right after `Create()` to bind its `Scintilla::ScintillaCall` (reached through `operator->()`, e.g. `m_Text->AppendText(...)`) to the control's direct-call function — no `SendMessage` round trip after that. The control is always `SC_CP_UTF8`; text in and out of the Scintilla API is `char` (UTF-8), so it goes through `ToUtf8`/`FromUtf8` (also in `ScintillaCtrl.h`) at the boundary with the rest of the app's wide strings. `DebugX/scintilla/ScintillaCall.cxx` is vendored, unmodified, upstream source (see `DebugX/scintilla/README.md`) — the vcpkg `scintilla` port builds the editor itself into `Scintilla.lib` but deliberately leaves this typed call layer as source for the consuming app to compile in, the same way SciTE does; its `AdditionalIncludeDirectories`/`PrecompiledHeader` overrides in `DebugX.vcxproj` are there because it is not part of the PCH and its quoted `#include`s need the vcpkg triplet's `scintilla` subdirectory specifically, not just the triplet's `include` root.
**Disassembly and Memory** are the other two Scintilla/HexControl-backed panes, both `CPaneBase<T>` (refresh only when dirty, visible and the target is stopped, like `CRegistersView`/`CCallStackView`, not the always-on-`OnOutput` pattern `CCommandView` uses). `CDisassemblyView` re-disassembles a fixed window of lines around the current instruction pointer on every refresh (`DebuggerX::Disassemble`, `GetInstructionOffset`) into its `CScintillaCtrl`, with an `::CreateLexer("asm")` Lexilla lexer (it ships with no instruction/register knowledge of its own — a mnemonic is plain `SCE_ASM_IDENTIFIER`, the default style, until `SetKeyWords` is given lists 0/1/2 (CPU/FPU instructions, registers), done once in `OnCreate`; `ApplyColors` then colors the resulting `SCE_ASM_*` styles from `SciLexer.h`, light/dark pairs redone on every theme change since `StyleClearAll` wipes them) and a symbol margin carrying two markers: a breakpoint circle (from `EnumBreakpoints`, clickable via `SCN_MARGINCLICK` to toggle one) and a current-line arrow. Its right-click menu (there is nowhere else for these yet) has Toggle Breakpoint and Run to Cursor (`ExecuteCommand(L"g <address>")` — the engine's own one-shot run-to, not a breakpoint DebugX manages itself). `CMemoryView` reads a fixed-size chunk at an address *expression* (`DebuggerX::Evaluate`, e.g. `@$csp`, architecture-neutral for "current stack pointer") into a `CHexControl` (`wtlhelper/HexControl`) each refresh via a fresh `MemoryBuffer`; the expression — not just the address it last resolved to — is what's kept, so it re-evaluates (and so can track a moving register) on every stop. **Writing to the target.** `CMemoryView` hands `CHexControl` a `TargetMemoryBuffer` (`TargetMemoryBuffer.h`, an `IBufferManager`): in overwrite mode every edit the control makes (typing, paste, Delete — which zero-fills —, undo/redo) goes through `SetData`, which updates the local copy and calls `DebuggerX::WriteMemory`; `Insert`/`Delete` refuse (target memory has a fixed size) and the Insert key is swallowed by a `SetWindowSubclass` on the control so it never enters insert mode. It is editable only for a live target that is stopped. `WriteMemory` raises `MemoryChanged` (→ `ISessionObserver::OnMemoryChanged`) before its task completes, which is how the Memory pane tells its own writes (`m_PendingWrites`) from someone else's (`eb` in the Command view, also mapped to `MemoryChanged` from the engine's data-only `ChangeDebuggeeState`). `CRegistersView` edits a value in place (a hidden `CEdit` over the cell; double-click, F2, Enter) in frame 0 of a live target, through `DebuggerX::SetRegister` (`EvaluateWide` to the register's type for integers, `wcstod` for floating point, `E_NOTIMPL` for vectors).
**Scope frame, Locals and Watch.** Double-clicking a call-stack row calls `DebuggerX::SetScopeFrame` (`SetScopeFrameByIndex`); the engine's `DEBUG_CSS_SCOPE` symbol-state callback becomes a `ScopeChanged` notification and `ISessionObserver::OnScopeChanged`. Registers are read with `GetValues2(DEBUG_REGSRC_FRAME)` (so they follow the frame), the Disassembly view starts at the frame's instruction with a green marker, and the engine's own thread walk (`EnumProcesses`) saves and restores the scope frame, since `SetCurrentThreadId` resets it. `CLocalsView`/`CWatchView` share `CSymbolPane<T>` (`SymbolPane.h`): a tree flattened into a virtual list of `SymbolEntry` rows. Expansion is by *path* (names from the root, `'\n'`-separated), passed to `GetLocals`/`EvaluateWatches`, which walk the values afresh each time and expand the matching ones — so no row index is ever held across refreshes. The values are the **debugger data model's** (`DbgModel.h`, as `dx` shows them), not symbol groups: `GetLocals` is the keys of `@$curframe.Parameters` and `@$curframe.LocalVariables` (which follow the scope frame), a watch is `IDebugHostEvaluator2::EvaluateExtendedExpression` (C++ syntax; one that does not evaluate is an error object whose display string is the reason), and `ValueWalker` (`DebugEngine/ValueWalker.h`) turns them into rows: a type with a visualizer (NatVis — the Windows Kits debugger's `Visualizers` folder has the standard library's; System32's and the package's engines have none, and show the fields) by its keys (`[size]`, ...) and elements, with its fields under `[Raw View]`; another structure by its base classes and fields (static ones and constants left out, by `IDebugHostField::GetLocationKind`) with a `{X=1 Y=2}` summary; an array (or anything iterable) by its elements (at most `MaxElements`); a pointer by what it points to (a `char`/`wchar_t` pointer also shows its string). A row also has a C++ `Expression` (`point.X`, `array[1]`, `(*shape.Next).X`; none under a visualizer's keys) when it is a number, a pointer, ...: **editing a value** (`CSymbolPane`: double-click the Value column, F2 in Locals, Edit Value) is `DebuggerX::AssignValue`, which evaluates `(expression) = (value)` with the data model and raises `MemoryChanged`. Watch expressions are edited in place (`LVS_EDITLABELS`, last row adds one) and kept in the pane's saved state after `|e:`, tab-separated. In a source file, the mouse resting on a name (with what it is a member of: `a.b`, `p->b`, `this->b`) or in the selection shows its value in a call tip (`SCN_DWELLSTART`, `EvaluateWatches`) while the target is stopped.
**Source files.** Unlike the panes of `PaneRegistry`, source files are dock panes made on demand: one `PaneKind::Document` pane per file, id `"source:" + path`, owned by `SourceDocuments` (a member of `CMainFrame`, which wires it into the dock's content factory, `SetPaneFactory` — so the files open at the last run come back with the layout — and `OnPaneClosed`, which destroys a closed source pane's window and removes the pane). On every stop, thread change and scope change it asks the engine where the scope frame is (`GetSourceLocations` on the thread's IP and, for a frame above 0, on its return address minus one: the call), opens that file *without taking the focus* (`DockLayout::Activate`, not `CDockHost::ActivatePane`; the first file goes in a group above the Command view, the next ones tab with it), and gives every `CSourceView` its arrows (`SetLocation`: yellow for the thread's line, green for the scope frame's). Where there is no source the status bar says why. `CSourceView` (`SourceView.h`) is a read-only Scintilla with the `"cpp"` Lexilla lexer (`lexer.cpp.track.preprocessor` off), line numbers and breakpoint markers it refreshes itself (`EnumBreakpoints` → `GetSourceLocations` of their offsets → its lines); it sets a breakpoint, and runs to a line (`g`), with the engine's `` `file:line` `` syntax, using the name the PDB has for the file when it is known (`SetSymbolFile`). F9 (when a source document is the active pane — `CMainFrame::OnDebugAddBreakpoint` sends it `ID_DISASM_TOGGLEBREAKPOINT`) and Ctrl+F10 (`ID_DEBUG_RUNTOCURSOR`, which the frame's `OnForward` passes to the active pane) act on the caret's line, as do Ctrl+Shift+F10 (`ID_DEBUG_SETNEXTSTATEMENT`, Set Next Statement) and, in the Disassembly view, the same three on the caret's instruction. **Set Next Statement** is `DebugManager::SetNextStatement` → `DebuggerX::SetInstructionOffset` (the IP register by the effective processor type, then `ResetScope` and `ContextChanged`, as `SetRegister`); an address in another function than the IP's (by symbol start) is refused with `SetNextOtherFunction` unless forced, and the UI asks first. **Restart** (Ctrl+Shift+F5) is for a session started by Run Executable (`CMainFrame::m_Launch`, cleared by any other start): it saves the breakpoints, `Stop`s, launches again and sets them again, as any run does (see Saved breakpoints). **Saved breakpoints** (`SavedBreakpoints.h`, `%LOCALAPPDATA%\DebugX\breakpoints.txt`): each program's, by its executable's full path (lowercase; for an attach, `QueryFullProcessImageName` of the process), are set again when it is next run or attached to (`CMainFrame::RestoreBreakpoints`, which then sets `m_BreakpointsKey`), and saved on each `OnBreakpointsChanged` while the target is stopped — not while it runs or ends, when the engine removes them itself; `SaveBreakpoints` checks again after `EnumBreakpoints` returns, since the notice that the session ended comes first. Code breakpoints only, not one-shot ones, and by `BreakpointInfo::Location`, not by address: the expression a breakpoint was set with, else `` `file:line` `` where a line starts, else `module!function+0x10` (`EnumBreakpoints`; a `bp` typed in the Command view has no expression, only an address, which the next run does not have). **Find and Go To**: Edit > Find (Ctrl+F, `CFindDlg`), F3 / Shift+F3 search the active pane's Scintilla control — `CMainFrame::ActiveTextControl` takes the first visible one among the pane's child windows, so a new Scintilla-based view gets Find for nothing — with `FindInScintilla` (`FindDlg.h`; it goes round past the end, and the status bar says so). Ctrl+G (`ID_EDIT_GOTO`) is passed to the active pane by `OnForward`: Go to Line in a source file, Go to Address in the Disassembly view (`CInputDlg`; it shows code from the address until the next stop, step, thread or frame change), the address box in the Memory view. `GetSourceLocations` finds a file through the source path (`FindSourceFileWide`), else where it was compiled. **Stepping**: F10/F11/Shift+F11 call `DebuggerX::Step(kind, bySourceLine)` — by source line unless the Disassembly pane is the active one. It sets the engine's code level (`SetCodeLevel`) for the one step and restores it, so `p`/`t` typed in the Command view are unaffected; it steps by instruction where the IP has no line information (a source-level `p` there would run on until it found some). A source-level `t` stops at whatever is called: Step Into follows jump thunks (incremental linking, imports), steps out of a function without lines (`gu`) and carries on with the line, so it ends in the next function that has source, or on the next line. **Paths**: `Options > Symbol and Source Paths` (`CSymbolPathsDlg`, an entry per line) edits the engine's paths (`GetSymbolPaths`/`SetSymbolPath`/`SetSourcePath`), saved in `AppSettings::SymbolPath`/`SourcePath` (empty: never set — `_NT_SYMBOL_PATH` and the like stand) and given to the engine at startup; `Debug > Reload Symbols` is `ReloadSymbols` (`.reload`, then `ContextChanged` so that the panes catch up). The engine is created with `SYMOPT_LOAD_LINES` (without it `` `file:line` `` still resolves, but warns "Line information loading disabled" each time).
**Sessions and panes, smaller things.** File > Recent Targets (`RecentTargets.h`, kept in `AppSettings::RecentTargets`, a tab-separated line each) is recorded by each successful start (`RunExecutable`, `AttachToProcess` with the process name — it attaches again to the one running process of that name —, `OpenDumpFile`, `AttachKernel`, `AttachLocalKernel`); the submenu is made again in `WM_INITMENUPOPUP` each time it opens (`ID_FILE_RECENT1..10`; the first is also in the menu resource, so `UpdateUI` enables it, or `CAutoUpdateUI` would). Debug > Save Dump is `DebuggerX::WriteDump` (a live target that is stopped; user mode: a minidump, with all of the memory as `.dump /ma` for "full" — which one is the save dialog's file type). Add to Watch (the Locals pane's right-click, which makes an expression of a member row from its parents; the source view's, for the selection or the word at the caret) is `AddToWatch` (`AppMessages.h`): `WM_ADDWATCH` to the frame (the root owner, also of a floating pane), which shows the Watch pane and passes it on. The Modules pane's right-click loads one module's symbols (`ReloadSymbols(image)`, `.reload /f`), opens its folder, copies its path; the Memory pane's sets the hex control's data size and bytes a line, kept with the address expression in its pane state.
**Kernel processes and threads.** The Processes pane (`CKernelProcessesView`) marks the process the debugger looks at (`DebuggerX::GetKernelProcess`, the implicit process) and switches to another (double-click, right-click: `SetKernelProcess` — `.process /p /r`, so user-mode memory and modules are that process's; `/i` and a `g` for a kernel over a connection only). The Kernel Threads pane (`CKernelThreadsView`, id `kthreads`) lists the implicit process's threads (`KernelProcessAnalyzer::GetThreadEnumerator` on the debug thread, start addresses by symbol) and switches to one (`SetKernelThread`, `.thread /p /r`; on a local kernel only the debugger's own thread has a context, so it fails for the others, and says why). Their Details items are `dt nt!_EPROCESS`/`dt nt!_ETHREAD`, not `!process`/`!thread` (see the extension DLLs below). `KernelAnalyzerBase::GetTypeId`/`GetFieldOffset` (and `KernelGlobals::GetVariable`) cache their answers by the kernel's base — failures too: public symbols lack some types (`_MM_SESSION_SPACE`, so `GetSessionId` is `InvalidSessionId` and the Session column empty), and a failed lookup searches all the symbols again, which made a walk of the processes take ~135 ms a process (with `DEBUGENGINETESTS_PROFILE=1` the `kernel` suite times each getter over all of them). **Threads and processes (user mode).** `EnumProcesses` gives each thread its name (`SetThreadDescription`), where it is (`module!function+0x10`), its suspend count and whether it is frozen — the last three are not in any API, so `Impl::EnumThreads` parses what `~` says, run with `Impl::ExecuteCaptured` (a command whose output goes to a string, not to the Command view: `Output2` appends to `m_Capture` while it is set, DML stripped). `SetThreadFrozen` (`~Nf`/`~Nu`) and `SuspendThread` (`~Nn`/`~Nm`) are the Threads pane's right-click; `SetCurrentProcess` the Processes pane's double-click (it lists the processes being debugged, the current one marked). Options > Debug Child Processes (`AppSettings::DebugChildProcesses`, `SetDebugChildProcesses`) launches with `DEBUG_PROCESS` alone (not `DEBUG_ONLY_THIS_PROCESS`) and runs `.childdbg 1` after an attach; a console program's `conhost.exe` is one of its children then, and stops at its start like any other. **Handles** (`CHandlesView`, live user mode): `EnumHandles` takes the process's handles from `NtQuerySystemInformation(SystemExtendedHandleInformation)` and their types and names from `ReadHandleData`, except the name of a file that `GetFileType` (which does not wait) says is not on a disk — asking a synchronous pipe with a read pending for its name never returns, and would hang the debug thread. **Memory search**: the Memory pane's right-click Search / Search Next (`SearchMemory`: hex bytes, `"text"` (UTF-8), `L"text"`; in user mode region by region through `QueryVirtual`, the committed readable ones). The Disassembly view shows each source line before its instructions (`GetSourceLocations`; Show Source Lines on its right-click, kept in its pane state): those lines have address 0 in `m_LineAddresses`, which the commands ignore. **Kernel panes**: Drivers, Object Namespace (a directory at a time; double-click a directory or an absolute symbolic link to go there, the first row to go up) and IRPs (the implicit process's threads, or all processes') run `KernelObjectAnalyzer` on the debug thread (`RunAsync`).
- **CDebugX** — a standalone console test/reference harness (`wmain`) that drives DbgEng directly (bypassing `DebuggerX`) to attach by PID, open a dump, or attach to the local kernel and run an interactive command loop. Useful as a minimal reference for DbgEng call sequences; it only borrows the notification data structs from `Debugger.h`.

Also present: `hello_imgui` and `imgui_bundle` git submodules (pulled in for the unrelated `Project1` ImGui experiment, not part of the debugger itself).

## Architecture: threading model

DbgEng requires all calls to `IDebugClient`/`IDebugControl` etc. for a given client to happen on the thread that created the client. `DebuggerX::Impl` runs a **dedicated debug thread** (`DebuggerThread()`, started by `Create()`) that sleeps in an alertable wait; engine calls are queued onto it with `QueueUserAPC`. Because a call such as `g` keeps that thread inside `WaitForEvent` until the target breaks, a queued request simply waits its turn.

**The UI thread never blocks on the engine and never runs a nested message loop.** Every engine operation on `DebuggerX` is a coroutine returning `DebugEngine::Task<T>`: it queues the work and suspends the caller; when the work is done the debug thread posts a message to a message-only window that `DebuggerX` creates on the calling (UI) thread, and that window resumes the coroutine there — so it works under any message loop, including modal dialogs. Callers either `co_await` the task or just drop it (a dropped `Task` lets the coroutine finish and free itself; the result is discarded). Pointer/reference arguments (the out parameters of `Enum*`) must stay valid until the task completes; string arguments are copied. `IsBusy()` is true while any task is in flight. Only `Break()` (`SetInterrupt`) may be used from other threads; `Create()` and the destructor block briefly (the destructor interrupts a running target, detaches/ends the session on the debug thread and waits up to 5 s).

A coroutine can resume after the window that started it is gone. A window that starts coroutines keeps a `Lifetime` member (`Lifetime.h`) and each coroutine does `auto alive = m_Lifetime.Watch();` before its first `co_await` and `if (!*alive) co_return;` after every one, before touching the window. Anything the engine thread uses while a task runs must not belong to a window (see the shared `Enumeration` in `KernelProcessesView`).

Engine events (breakpoints, exceptions, thread/process create/exit, output text, execution-status changes) arrive on `IDebugEventCallbacks`/`IDebugOutputCallbacks2` implemented by `Impl` itself, on the debug thread. They are queued under a mutex (with a single coalesced wake-up message, so a flood of output cannot overflow the message queue) and delivered on the UI thread to the `NotificationHandler` passed to `Create()`. The data pointer is only valid during the call — the debugger frees it afterwards, receivers never do. `DebugManager` passes them to the `SessionModel` (`SessionModel.h`), which turns them into typed events for the `ISessionObserver`s registered with `AddObserver`/`RemoveObserver` (windows add themselves when created and remove themselves in `WM_DESTROY`): `OnSessionChanged` (status, busy or target changed — re-derive your controls from `Session()`), `OnBroke`/`OnResumed`, `OnContextChanged` (the current thread changed, or the target broke), `OnScopeChanged` (another frame of the current thread's stack was chosen — `SessionModel::CurrentFrame()`; stops and thread changes reset it to 0 without this event), `OnBreakpointsChanged`, `OnModuleLoaded`/`Unloaded`, `OnTargetAttached`/`OnTargetEnded`, `OnThreadCreated`/`Exited`, `OnProcessCreated`/`Exited`, `OnOutput`, `OnLogLine` (the bounded event log the Output pane shows). It all runs on the UI thread, so there is no locking and no cross-thread `SendMessage`. The engine adds two payload-free notifications for state a caller can otherwise only poll: `BusyChanged` (a call went in flight / the last one completed) and `TargetChanged` (attached, opened, or — when the status becomes NoDebuggee — ended, which resets `GetTargetType()` to Unknown). The execution status is tracked from `StatusChanged` payloads (in order with the other events), not read from the engine.

`Impl` is a COM object whose references are held by the engine (as its callbacks); the engine lets go of them on the debug thread when the client is released. `DebuggerX` therefore holds a reference of its own and releases it only after the shutdown request has run — do not `delete` the object.

## Conventions to know

- Generic UI helpers come from WTLHelper, not from local copies: `CVirtualListView<T>` (virtual list views; callbacks are `GetColumnText(HWND, row, col)`, `GetRowImage(HWND, row, col)`, `DoSort(const SortInfo*)`), `SortedFilteredVector<T>` (STL-style names: `push_back`, `clear`, `size` = filtered size), `SortHelper::Sort`, `CDialogHelper<T>` (`AdjustOKCancelButtons(okIcon, cancelIcon)`, `AddIconToButton`), `SecurityHelper`, `IconHelper`, `ToolbarHelper`. DebugX's include path has `wtlhelper/WTLHelper`, so `#include "SortHelper.h"` etc. resolve there; add a helper to WTLHelper rather than to DebugX when it is not DebugX-specific.

- `TargetType` is a flags enum (`DEFINE_ENUM_FLAG_OPERATORS`) — check kernel vs. user targets with bitwise `&` (e.g. `GetTargetType() & TargetType::Kernel`), not equality.
- The `HR(x)` macro (defined locally in each `.cpp` that uses it) early-returns the enclosing function on a failed `HRESULT` — it assumes the enclosing lambda/function returns `HRESULT`. Use it inside the lambdas that run on the debug thread, not in a coroutine body (`return` is not allowed there).
- The UI state of the toolbar/menus (`CMainFrame::UpdateUI`, which also enables each View-menu pane command from its `PaneInfo::Requires`) and of the Command view is derived from `DebugManager::Session()` in `OnSessionChanged`; nothing polls, and nothing else sets it. A new pane goes in the `PaneRegistry` table *and* needs its own `COMMAND_ID_HANDLER(ID_VIEW_x, OnViewPane)` line in `CMainFrame`'s message map — `MainFrm.h`'s trailing `COMMAND_RANGE_HANDLER(0x8000, 0xffff, OnForward)` silently swallows a `ID_VIEW_*`/other menu command in that range that has no handler of its own, so a forgotten line looks like the menu item does nothing, not like a build or runtime error. Observer member names must not collide with the mixed-in classes' (`CVirtualListView` has its own `OnStateChanged`, `CWindow` has `Invalidate`).
- Pitfalls found in the panes: a virtual list (`LVS_OWNERDATA`) never notifies a check box toggle — hit-test in `OnListViewClick` (`LVHT_ONITEMSTATEICON`); `CListViewCtrl::GetSelectedIndex` asserts unless `LVS_SINGLESEL` (use `GetNextItem(-1, LVNI_SELECTED)`); `CVirtualListView`'s double/right click handlers use `GetCursorPos`; `IDebugControl::RemoveBreakpoint2` frees the breakpoint, so `Detach()` the `CComPtr` before calling it (a Release afterwards is a use-after-free on the debug thread).
- Debug commands also come from accelerators (F5, F10, F11, Ctrl+Break, ...), and `CUpdateUI` only brings a menu item's enabled state up to date when its popup opens — so a command handler must check `DebugManager::Session()` itself (`CanRun()`, `CMainFrame::CanStartSession()`) rather than rely on `UIEnable` having grayed it out.
- WTLHelper's `Settings::Set<T>` does not update the stored `Size`, so a setting must be read and written with the same type it was declared with in `BEGIN_SETTINGS` (a `SettingType::Bool` declared with `1` is 4 bytes; writing a `bool` to it overruns on save) — declare on/off settings as `Int32` and use `int`, as `DarkMode`/`Dml` do.
- Scintilla pitfalls: unlike RichEdit's `AppendText`, `SCI_APPENDTEXT` (`ScintillaCall::AppendText`) still checks `SCI_SETREADONLY` (`Document::InsertString` does the check) — a read-only log view has to toggle it off/on around its own appends, see `CCommandView::AppendText`. A DML/hyperlink-style run is a Scintilla *hotspot* style (`StyleSetHotSpot`), not manual hit-testing: style the run, catch `SCN_HOTSPOTCLICK`'s `NotificationData::position` (a byte offset — the control is UTF-8) instead of chasing `WM_SETCURSOR`/`CharFromPos`. `GenericEditCommands.h`'s Select All/Clear All special-case a focused window whose class name contains "Scintilla" (it is ATL-superclassed to `"ATL:Scintilla"`, never checked as an exact match) to send `SCI_SETSEL`/`SCI_CLEARALL` instead of the `CEdit`-style calls that plain `EM_*` messages need. Scintilla does not send `NM_RCLICK`; a pane's own right-click menu is a `WM_CONTEXTMENU` handler on the contained window's `ALT_MSG_MAP`, as `CDisassemblyView` does.
- `CHexControl` (`wtlhelper/HexControl`) is built on `CBufferedPaintWindowImpl`, from `<atltheme.h>` — not part of `stdafx.h`'s own include chain, so a view that uses it (`MemoryView.h`) includes it explicitly before `SimpleHexControl.h`, or every method the base class should have supplied errors out as if `CHexControl` had no base class at all.
- Breakpoints: `DebuggerX::AddBreakpoint`/`UpdateBreakpoint` take a `BreakpointSettings` (code or data, condition, command, pass count, thread, one-shot, enabled); `CBreakpointDlg` edits one. The engine has no breakpoint conditions: DebugX keeps the condition (and a hit count) itself, keyed by `IDebugBreakpoint3::GetGuid` — not by id, which the engine reuses, also after a `bc` typed in the Command view — and evaluates it as `@@c++(...)` in the `Breakpoint` event callback, returning `DEBUG_STATUS_GO` when it is zero (the engine then does not run the breakpoint's command either); a condition that does not evaluate breaks. `IDebugBreakpoint2` does not derive from `IDebugBreakpoint`, so helpers that take either use `IUnknown*`. A breakpoint on a function name is on its first instruction, before the prologue: a condition on its *arguments* reads them before they are where the PDB says (see the symbol group note below) and does not evaluate, so it breaks every time — a source line (`` `file.cpp:N` ``) or an address inside the body works. Data breakpoints are evaluated to an address once (`SetOffset`), must be aligned to their size (1/2/4/8), and cannot change type on update (`E_INVALIDARG`).
- Exceptions and events: whether one breaks is the engine's event filters' decision (`DebuggerX::GetEventFilters`/`SetEventFilters`, edited by `CExceptionSettingsDlg`, Debug > Exception Settings); `Impl::Exception` returns `DEBUG_STATUS_NO_CHANGE` and only reports the exception (`ExceptionData`, logged to the Output pane) — a callback that returns `DEBUG_STATUS_BREAK` overrides the user's choice. Specific events are matched by name, exceptions by code (one the engine has no filter for is added; `SetEventFilters` removes the added ones not in the list it is given); the filter with code 0 is the engine's "Unknown exception", the policy for every code without its own. The defaults are captured when the engine is created (`GetEventFilters(..., true)`); only the differences from them are saved (`AppSettings::EventFilters`, `EventFilterText`) and re-applied at startup, so a newer engine's defaults still hold for the rest. The filters belong to the engine, not to a session: they carry over from one target to the next.
- `GetValues2(DEBUG_REGSRC_FRAME)` (and the symbol groups) read the *scope's* copy of the register context, which `IDebugRegisters::SetValue` does not update — `SetRegister` calls `ResetScope()` afterwards, or the Registers pane shows the old value. A data-only `ChangeDebuggeeState` also arrives while a step is executing, so it means "memory was written" only when the status is `DEBUG_STATUS_BREAK`.
- **Which dbgeng.dll.** `DebugX.exe` delay-loads it, and `DebugManager::Init` picks it before the engine is created (`DebugEngine::LoadEngine(EngineSource::Automatic)`, `EngineLoader.cpp`): the Windows Kits debugger's (`WindowsKitsDebuggersFolder`: `...\Windows Kits\10\Debuggers\<arch>\`, from the registry's Installed Roots, else the default install folder), loaded with `LOAD_WITH_ALTERED_SEARCH_PATH` so its own `dbghelp.dll`, `symsrv.dll` and extension DLLs come with it; else System32's. The status bar says which at startup. The NuGet package's DLLs (`DebugEngine/amd64`) are not used by the app (only by the tests). System32's differs from the others: its `IDebugSymbols5::GetCurrentScopeFrameIndex` fails (`E_OUTOFMEMORY`) for any frame, so the scope frame's index is read through `Impl::GetScopeFrameIndex`, which falls back to `GetScope`'s `DEBUG_STACK_FRAME::FrameNumber`. Also, at the initial break it has loaded no symbols, and a `` `file:line` `` (a breakpoint, `g`) is looked up only in loaded ones — it becomes a deferred breakpoint that never hits — so `LaunchAndAttach`/`AttachToProcess` load the executable's symbols there (`Impl::LoadExecutableSymbols`, `.reload /f <exe>`). Test engine changes against both DLLs (`DebugEngineTests` does, see Build). **System32's and the package's engines have no `symsrv.dll` and no extension DLLs** (`ext`, `exts`, `uext`, `kdexts`, ...; only the Windows Kits debugger has them — which is why it is preferred): `srv*` elements of the symbol path are ignored (`DBGHELP: x.pdb - file not found`, no `SYMSRV` lines with `!sym noisy`) — only a PDB the image points to, or one in a plain folder, loads; Windows' own modules, and the kernel, get export symbols only — and every `!`-command fails. `symsrv.dll` is looked for next to the `dbghelp.dll` the engine uses (the application's folder does not do for System32's). The engine's own breakpoints (the one `gu` or `g <address>` runs to) also come to the `Breakpoint` callback; they are not in its list (`GetBreakpointById` fails for their id).
- Building one project on its own (`MSBuild DebugEngine.vcxproj`) puts its output somewhere other than the solution build does (`$(SolutionDir)` is not set); build `DebugX.sln`.
- Data model: `IModelObject::EnumerateRawValues` on a synthetic object (`@$curframe.LocalVariables`) crashes inside `dbgmodel.dll` — call it on `ObjectTargetObject`s only. Every object has method keys (`Where`, `Select`, `ToDisplayString`, ...): skip `ObjectMethod` values. A native number or pointer is an `ObjectIntrinsic` with no location (`GetLocation` fails), so it is assigned through an expression, not written to memory. At a breakpoint on a function's first instruction, a debug build's locals and arguments read `<Memory access error>`: they are addressed from a frame register the prologue has not set up yet; that is not a DebugX bug.
- Kernel process/thread walking (`DebugX.Kernel`) reads target memory/symbols directly (e.g. `_EPROCESS` linked lists) rather than using `IDebugSystemObjects`, since that API only works for live user-mode/live-kernel targets, not always applicable — check `KernelAnalyzerBase`/`KernelGlobals` before assuming a helper works for dumps.
